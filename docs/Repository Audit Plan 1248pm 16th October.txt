# 4. Product behaviour that must be protected

Pay particular attention to these principles.

## Natural narration

A person should be able to describe several financial events in one ordinary narration.

CashNarra should:

**understand → clarify only what materially matters → present a compact review → save correctly.**

Core rule:

**Don't confirm the obvious. Clarify the important.**

## Financial meaning

CashNarra must distinguish concepts such as:

- income versus money received;
- expenses versus every outgoing payment;
- sales versus debt settlement;
- loan proceeds versus revenue;
- principal repayment versus expense;
- owner contribution versus sales;
- owner withdrawal versus operating expense;
- transfer versus spending;
- credit sale versus cash receipt;
- stock purchase versus automatically recognised profit expense;
- goal allocation versus actual expenditure.

The UI may hide accounting jargon.

The internal financial system must not hide accounting correctness.

## AI boundary

AI interprets language and can explain results.

AI must **not** be the authoritative ledger or calculator.

Expected conceptual flow:

**Natural language 
→ structured interpretation 
→ deterministic/domain validation 
→ necessary clarification 
→ user review/confirmation 
→ deterministic posting 
→ ledger 
→ deterministic calculations 
→ AI explanation**

Official totals, balances, posting, authorisation and forecasts must not depend on an LLM inventing arithmetic.

## Trust

Important numbers should be traceable to their underlying records.

CashNarra should not claim certainty it does not possess.

Examples:

- don't call every inflow revenue;
- don't call every outflow an expense;
- don't claim profit if the available information cannot support profit;
- don't imply an account is bank-verified when it is only manually recorded;
- don't treat missing information as zero;
- don't say something was saved until authoritative persistence actually succeeded.

### Important ownership rules

`AGENTS.md`

Only durable repository-specific operating rules and non-negotiable CashNarra invariants.

Do NOT turn it into a giant product specification.

`GOALS.md`

The frozen remediation outcome, success conditions, hard constraints and non-goals.

`PLANS.md`

Ordered phase sequence and status.

`harness/build/<phase>.md`

Exact scope, acceptance criteria and validation for that phase.

`harness/context/<phase>.md`

Only material discoveries, decisions, constraints and unresolved questions that a future Codex session would otherwise need to rediscover.

`harness/build-log.md`

Observed progress and verification evidence.

It must say what actually happened, not what was planned.

### Git is the primary checkpoint

Tell Codex to work on a dedicated branch.

Before implementation:

- record baseline branch;
- record baseline HEAD SHA;
- ensure unrelated user changes are not destroyed.

At every completed phase:

1. run the phase validations;
2. fix failures before proceeding;
3. update phase context if necessary;
4. update build-log with actual evidence;
5. update plan status;
6. inspect `git diff`;
7. commit the completed phase with a descriptive commit;
8. record the resulting commit SHA.

Do not bundle several unrelated phases into one giant commit.

### Interruption safety

In addition to completed-phase commits, Codex must leave a recovery checkpoint after a meaningful atomic unit whenever substantial work is in progress.

A checkpoint must state:

- timestamp;
- branch;
- current HEAD;
- current phase;
- exact objective;
- completed work;
- files changed;
- tests already run and results;
- current working-tree status;
- unfinished work;
- known broken state if any;
- blockers/questions;
- exact next recommended action;
- commands needed to resume;
- assumptions made.

Never record secrets.

If an implementation is knowingly half-finished and does not pass validation, say so explicitly.

Do not falsely mark it complete.

### Resume protocol

A new Codex session should be able to begin with something like:

1. Read repository `AGENTS.md`.
2. Read `GOALS.md`.
3. Read `PLANS.md`.
4. Read `harness/build-log.md`.
5. Identify the current phase.
6. Read only that phase's build file and relevant context.
7. Check current branch, HEAD and worktree.
8. Run a small sanity verification.
9. Continue from the recorded next action.
10. Do not repeat completed discovery unless repository evidence contradicts the checkpoint.

Write the exact reusable **RESUME PROMPT**.

# 4. What the repository got right

A lot.

These areas should be protected from unnecessary rewrites.

## Exact-money handling

`money.ts` uses `decimal.js`, string boundaries, explicit two-decimal validation and tabular GH₵ formatting rather than authoritative JavaScript floating-point arithmetic. 

This directly satisfies one of the most important architectural requirements.

**KEEP.**

## Hidden double-entry semantics

The ledger distinguishes:

- sale;
- other income;
- expenses;
- stock;
- asset purchase;
- transfers;
- credit sales;
- unpaid stock purchases;
- debt receipts;
- payable settlements;
- loans;
- loan principal;
- loan interest;
- owner contributions;
- owner withdrawals;
- opening receivables/payables/loans.

The human labels are intentionally not accounting jargon. 

**KEEP.**

## Transfer correctness

Transfers debit one cash account and credit another, and reports exclude them from received/paid totals.

This is tested at the domain layer and at database level.

**KEEP.**

## Debt settlement avoids double-counting

Receivable settlement posts:

```text
cash ↑
receivable ↓
```

instead of creating another sale.

Likewise payable principal reduces the payable rather than becoming another operating expense.

The SQL posting templates enforce those semantics. 

**KEEP.**

## Stock is not automatically expensed as profit cost

A stock purchase posts into a stock account rather than the general expense account.

The report consequently refuses to invent profit.

The current report returns `profit: null` and explicitly explains that cost-of-sales and other information are missing. 

This is exactly the kind of financial honesty the source demanded.

**KEEP.**

## Unknown is not zero

Unknown account openings can remain `null`.

Balances remain unknown rather than becoming GH₵0.00.

This distinction has explicit tests. 

**KEEP.**

## Corrections preserve history

Posted records are not silently overwritten.

The implementation preserves old records and correction history, including source provenance and opening-balance history.

Database rules explicitly reject arbitrary rewriting of financial history. 

**KEEP.**

## Atomic saves and retries

This is one of the strongest areas.

`commit_workspace`:

- uses a request key;
- stores a payload hash;
- returns the existing receipt for a valid retry;
- rejects reuse of the same ID with different content;
- checks expected workspace version;
- takes a transaction-level advisory lock;
- validates the candidate state;
- rebuilds journal lines;
- checks journal balance;
- stores state and receipt together.

Two-workspace moves lock both workspaces in deterministic order. 

The UI also preserves the original request when the network outcome is unknown and asks the server for the receipt before retrying. 

That is exactly the behaviour CashNarra needs.

**KEEP.**

## Tenant isolation architecture

The application uses the user's Supabase session and `auth.getUser()`, not a browser-exposed service-role credential. 

Tables have RLS enabled, broad write grants are revoked, and the mutation RPC checks `auth.uid()` ownership again.

The database harness explicitly exercises cross-user reads and writes. 

**KEEP + HARDEN**, not replace.

## AI is not the ledger

This is correctly implemented architecturally.

The model:

- has no database credentials;
- does not receive SQL tools;
- proposes event structures;
- cannot decide workspace access;
- cannot post;
- cannot calculate authoritative totals;
- cannot claim a record was saved.

`realExtract()` is followed by deterministic validation. 

That is directly aligned with the product's core financial architecture. 

**KEEP + HARDEN.**

## Goal forecasts are deterministic

The goal calculation is ordinary TypeScript/Decimal logic rather than an AI prediction.

It:

- counts actual allocations;
- checks three completed months;
- refuses dates when months/commitments are unknown;
- uses an explicit pace;
- treats what-if as isolated;
- produces no completion date at zero/negative pace;
- doesn't mutate actual allocations.



**KEEP.**

## Narra v2 is actually implemented

The current UI is not the rejected v1 Storyline design.

The code contains:

- v2 semantic tokens;
- violet/ink/apricot roles;
- light/dark themes;
- reduced-motion tokens;
- Manrope/Inter typography;
- Today/Records/Money Stories/Plan;
- mobile bottom navigation;
- a prominent narration composer;
- unboxed transaction rows;
- Money Story presentation;
- recorded-balance wording;
- explicit “manually tracked” account text;
- rhythm copy that says a check-in does not prove complete records.

 

**KEEP.**

## The review workflow understands “saved” correctly

Draft states include:

- waiting for processing;
- needs clarification;
- ready to review;
- saving;
- save not confirmed;
- receipt recovery;
- saved.

The review screen says proposed records are **not saved yet**. 

**KEEP.**

## Offline behaviour is intentionally modest

The app does not pretend to have a fully offline ledger or AI.

IndexedDB stores private-device drafts, scoped to account/workspace, with stale revision protection. 

The service worker only caches public brand assets rather than authenticated financial responses. 

That is exactly the appropriate V1 boundary.

**KEEP + HARDEN.**

# 5. Where the repository has drifted

The drift is smaller than I expected, but important.

## The implementation sequence drifted toward secondary complexity before proving the core AI

The agreed sequence was:

1. financial core;
2. text narration/review;
3. reports;
4. goals;
5. voice after text validation.

Instead, the repository has already accumulated substantial voice-recorder/container/parser/recovery work while representative real narration interpretation remains unvalidated.

This is not reason to delete the voice code.

It is reason to **stop investing in it for now**.

## “Payables” are implemented too narrowly

The product source says CashNarra should understand **payables**, not merely “stock bought on credit.”

The current event type exposed to users is effectively:

> **Unpaid stock purchase**

and SQL always posts `credit_purchase` as:

```text
stock asset ↑
payable ↑
```

 

Therefore this ordinary statement is not represented correctly:

> “The electrician fixed the shop for GH₵800 and I will pay him next week.”

That should be an expense/payable, not stock/payable.

This is a real financial semantics gap.

## The app structure retained too much prototype centralisation

The v2 handoff expressly said to translate the interactive preview into reusable components rather than ship the monolithic prototype. 

Yet `src/components/cashnarra.tsx` is an enormous client-side controller containing navigation, loading, offline drafts, narration, review, records, stories, planning and multiple dialogs.

The UI itself is aligned.

The structure is not yet aligned with the handoff's intended maintainability.

## Full workspace state is repeatedly transported

`store.list()` selects entire JSON workspace states.

`get()` obtains one workspace by calling that list operation and then finding it in memory.

After successful writes the client calls `refresh()` and re-downloads all workspace states. 

For today's synthetic dataset this is fine.

For “financial memory” accumulated over years, it conflicts with the low-data/modest-device goal.

This does **not** justify normalising the whole database today.

It justifies improving the read boundary.

## Development history is not checkpointed in Git

The code may have undergone many disciplined internal passes, but the public repository has one giant commit.

For a project you intend Codex to continue autonomously, that is dangerous.

The repository currently remembers progress through a huge historical `BUILD-STATUS.md`, not through clean phase commits.

That should change immediately.

## CN-P1-01 — General narration intelligence is not yet proven

**Severity:** P1 
**Category:** Core product / AI

**Source requirement:** CashNarra's defining promise is converting an entire natural narration into trustworthy records with only necessary clarification. 

**Repository evidence:** `mockExtract()` accepts exactly two labelled synthetic strings and rejects everything else. The real Responses API adapter exists, but no representative evaluation corpus or scored live evaluation is present. 

**Current behaviour:** Development/demo flows prove the mechanics of extraction → clarification → review → save, but not the quality of arbitrary financial understanding.

**Why it matters:** This is CashNarra's core product, not an optional AI enhancement.

**Desired behaviour:** Representative Ghanaian money narratives reliably become correct event proposals or appropriate clarification questions, without making up missing facts.

**Recommended action:** Build the evaluation harness before further feature work.

Initial corpus should cover at least:

- multi-event days;
- sales vs cash receipts;
- credit sales;
- debt settlements;
- partial settlements;
- supplier payables;
- transfers;
- owner contributions;
- owner withdrawals;
- loans;
- principal/interest;
- stock;
- ambiguous dates;
- ambiguous payment accounts;
- correction instructions;
- splits;
- workspace moves;
- colloquial GHS expressions;
- “4k”, “two five”, “momo”;
- irrelevant text;
- prompt-injection-like narration;
- missing amounts;
- uncertain parties.

Keep the gold data synthetic but human-reviewed.

**Dependency:** CN-P1-02 and CN-P1-04.

**Verification:** Every designated financial-integrity case must either produce the correct proposed meaning or explicitly require clarification. There must be zero direct posting by the model and zero invented authoritative totals.

## CN-P1-03 — General operating payables cannot be represented correctly

**Severity:** P1 
**Category:** Financial integrity / scope completeness

**Source requirement:** V1 explicitly includes receivables **and payables**. 

**Repository evidence:** `credit_purchase` is labelled “Unpaid stock purchase” and posts only:

```text
Dr stock
Cr payable
```



**Current behaviour:** Stock purchased on credit works. Ordinary operating expenses incurred but not yet paid do not have a truthful representation.

**Why it matters:** Encoding an unpaid electricity bill, contractor service or delivery expense as stock is financially wrong; recording it only when paid puts expense recognition in the wrong period.

**Desired behaviour:** CashNarra can represent both:

```text
Stock bought on credit:
Dr Stock
Cr Payable
```

and:

```text
Operating expense incurred on credit:
Dr Expense
Cr Payable
```

**Recommended action:** Add the smallest additional event kind, e.g.:

```text
credit_expense
```

Human label:

> Expense to pay later

Do not create a generic accounting subsystem.

Update:

- `types.ts`;
- `ledger.ts`;
- SQL posting template;
- manual form;
- AI prompt/schema semantics;
- obligations logic;
- reports;
- exports;
- fixture/eval cases;
- TS↔SQL parity tests.

**Dependency:** Financial phase before AI evaluation baseline.

**Verification:** Incurred expense appears in period expense immediately, payable increases, later payment reduces payable and cash without creating another expense.

## CN-P1-04 — AI clarification/context schema does not yet fully model important ambiguities

**Severity:** P1 
**Category:** AI/domain boundary

**Source requirement:** “Clarify the important” in human language.

**Repository evidence:** `realExtract()` receives account lists and obligations but does not pass the workspace type in its structured context. Its clarification schema can ask only about:

```text
accountId
kind
amount
obligationId
date
```

It cannot first-class identify missing `party` or `toAccountId`. 

**Current behaviour:** Some errors fall into a generic “review the meaning/date/account/linked balance” clarification instead of a precise human question.

**Why it matters:** Questions such as:

> “Which of your accounts did you move it to?”

and:

> “Who do you owe?”

are exactly where CashNarra's product quality lives.

Workspace type also informs business owner-money semantics.

**Desired behaviour:** Structured, deterministic clarification reasons that can express every financially material missing field.

**Recommended action:**

- pass `workspace.type`;
- extend clarification fields with at least `party` and `toAccountId`;
- distinguish model-proposed uncertainty from deterministic validation failures;
- have the application generate durable event IDs after parsing rather than treating arbitrary model IDs as authority;
- use human-language question templates where deterministic context is sufficient.

**Dependency:** CN-P1-03 event model; CN-P1-02 model migration.

**Verification:** Eval cases for every clarification type, including correct no-question cases.

**Category:** Security hardening

**Source requirement:** strict workspace isolation and narrow privileged operations.

**Repository evidence:** current functions are `security definer`, placed in `public`, and set `search_path=public,pg_temp`. They do revoke broad execute grants and perform explicit ownership checks, which is good. 

Current Supabase guidance now recommends keeping security-definer functions out of exposed schemas and using `search_path=''` with schema-qualified objects. ([Supabase](https://supabase.com/docs/guides/database/functions))

**Current behaviour:** No exploit demonstrated; ownership checking is strong.

**Desired behaviour:** Equivalent functionality with a smaller privilege surface.

**Recommended action:** Migrate privileged implementation functions to a private schema where practical, schema-qualify all referenced objects, pin an empty search path, and expose only narrow authenticated RPC wrappers if needed.

Do not casually change ownership/permissions.

**Dependency:** SQL parity tests first.

**Verification:** Repeat all cross-user, concurrent, retry and rollback tests against the migrated functions.

```text
└─────────────────┬─────────────────────────────┘
                  │ authorised HTTPS
                  ▼
┌───────────────────────────────────────────────┐
│             NEXT.JS SERVER BOUNDARY           │
│                                               │

│                                               │

└─────────────────┬─────────────────────────────┘
                  │ user reviews/confirms
                  ▼
┌───────────────────────────────────────────────┐
│              SUPABASE POSTGRES                │
│                                               │

                  │
          ┌───────┼────────┐
          ▼       ▼        ▼
      Reports   Goals    Exports
       SQL/TS    TS       CSV/PDF/XLSX
          │
          ▼
 AI explanation may explain supplied facts
 but never create official numbers
```

## Client responsibilities

The browser may:

- capture words;
- persist optional private-device drafts;
- display proposals;
- collect clarification;
- allow edits;
- render authoritative server data;
- render deterministic scenarios.

It must not be authoritative for:

- workspace access;
- official journal posting;
- save success;
- official totals;
- final duplicate prevention.

## AI boundary

Keep approximately:

```text
src/server/ai/
  extractNarration
  interpretCorrection
  explainPeriod
```

No agent framework.

No vector database.

No autonomous SQL.

No AI-generated balance.

Add an explicit evaluation contract.

## Event/domain model

Retain the current event model but close the payable gap:

```text
sale
income
expense
credit_expense       ← add
stock
credit_purchase
asset
transfer
credit_sale
receivable_payment
payable_payment
loan_received
loan_principal
interest
owner_in
owner_out
opening_receivable
opening_payable
opening_loan
```

Do not attempt full GAAP/IFRS accounting software.

## Database model

Do not perform a major normalisation rewrite.

The current deliberate approach is documented as a versioned workspace aggregate plus deterministic journal projection and receipts. 

That is acceptable for V1.

Improve read efficiency before reconsidering storage architecture.

A future normalisation trigger should be measured, such as:

- workspace payload becoming materially slow;
- report queries requiring excessive client transfer;
- histories exceeding practical update sizes;
- concurrent collaboration becoming required.

Not merely “relational databases should be normalised.”

## Corrections

Continue:

```text
posted record
   ↓ correction
mark prior effect removed
   +
append replacement
   +
append correction history
```

Do not silently mutate posted facts.

## Provenance

Continue retaining:

```text
record → sourceId → narration/evidence metadata
```

while permitting source text minimisation separately.

## Reports

Authoritative values come from ledger/records.

AI explanation can receive:

```text
record IDs
event meanings
already-computed summaries
known exclusions
```

and explain them.

Do not ask it:

> “Read this month and calculate my profit.”

## Goals

Keep goal allocations separate from spending.

Keep basic current-pace scenario only.

Do not yet implement:

- investment returns;
- probabilistic market forecasts;
- credit recommendations;
- sophisticated Monte Carlo;
- “you can afford this” claims.

## Offline

Keep V1 deliberately modest:

```text
offline → retain draft locally
online → process draft
user reviews
authoritative server save
```

Do not synchronise the entire ledger offline.

## What threatens CashNarra most right now
