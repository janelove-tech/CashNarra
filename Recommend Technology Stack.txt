### Managed services versus self-hosting

These are materially different choices:

- **Managed Supabase:** the provider operates PostgreSQL, authentication infrastructure, and database backups. You still own permissions, schema changes, retention, incident response, and restoration verification.

**I would not self-host the full Supabase bundle for the first release.** Subscription savings would need to outweigh server administration, restore work, and responsibility for outages.

### Financial integrity: a small hidden double-entry ledger

**Yes—hidden double-entry is appropriate from the beginning.** It provides a consistent way to distinguish transfers, debts, owner money, stock, and spending while keeping the interface conversational.

Use a small set of internal accounts and posting templates. Users see “loan received” or “Sandra paid her balance,” rather than journal terminology.

The minimum rules are:

1. **Exact money.** Store GHS amounts as PostgreSQL `NUMERIC(20,2)`. Transfer amounts through application boundaries as decimal strings. Use decimal.js where application arithmetic is necessary. Do not calculate money using ordinary JavaScript floating-point arithmetic. Define rounding rules explicitly.

2. **Atomic posting.** “Save all” invokes one database transaction. Journal lines, debt links, and batch status commit together. Transfers contain both account movements in that transaction. A failed batch changes nothing.

3. **Retry protection.** Every submission has a unique request ID scoped to its workspace. Repeating a successful request returns the existing result. Similar date/amount/person matches produce duplicate warnings, not automatic deletion.

4. **Concurrency protection.** Lock the batch and affected obligations while posting. Use versions to detect stale edits. Two tabs cannot settle the same outstanding balance twice.

5. **Controlled states.** Narrations produce drafts; unresolved material questions keep affected records in review. Only confirmed, posted records affect reports.

6. **Traceability.** Retain the confirmed financial facts, source ID, relevant dates, actor, interpretation version, and correction links. Raw source content can expire separately.

Posted journals must balance within their workspace and currency. Database controls should reject invalid account relationships and unbalanced posting.

| Event | Financial treatment |
|---|---|
| New cash sale | Cash receipt and sales |
| Credit sale | Receivable and sales; no cash receipt yet |
| Customer pays an existing debt | Receipt and reduced receivable; no second sale |
| Loan received | More cash and a liability; no sales revenue |
| Loan repayment | Principal reduces liability; interest is separately classified |
| Owner contribution/withdrawal | Owner money; distinct from sales and operating expenses |
| Internal transfer | Account balances change; workspace total cash does not |
| Stock purchase | Cash outflow and stock acquired; not automatically cost of goods sold |

**Initial reports should show cash movement, recorded sales, operating expenses, stock purchases, owner money, and outstanding obligations.** When inventory consumption, tax treatment, depreciation, or other necessary information is absent, say that profit cannot yet be determined.

Balances should be labelled **“recorded balance”**, with the last user check shown separately.

#### Corrections and removal

Drafts can be edited or discarded normally.

For posted records:

- “Change this” creates a linked reversal and replacement.
- “Delete this duplicate” voids its financial effect and hides it from normal reports.
- Splits preserve the original total.
- Corrections involving settled debts or another workspace require dependency checks.
- A privacy deletion request follows the retention process in section D.

The interface can remain simple while the financial history remains consistent.

### AI: interpretation through a small boundary

Use one internal module with operations such as:

- `extractNarration`
- `interpretCorrection`
- `explainSummary`

Initially, use the pinned GPT-4.1 Mini snapshot through the Responses API with Structured Outputs. This is a cost/latency starting choice, subject to evaluation—not proof that it understands Ghanaian financial narration adequately.

Schema validation checks output shape. Domain validation checks financial meaning: accounts, dates, amounts, debt references, sales-versus-receipt ambiguity, and principal/interest splits. Use explicit missing fields and clarification reasons. Do not present model-generated “93% confidence” as a calibrated probability.

**The model receives no database credentials and cannot decide workspace access, post records, calculate official totals, or authorise corrections.**

Conversational queries use narrow server operations: search authorised records, retrieve a period summary, retrieve an obligation, or propose a correction. The server validates every record ID and operation.

Treat narration and future uploads as untrusted content. Instructions inside them cannot change system permissions. SQL queries and bounded context are sufficient initially; no retrieval framework, vector database, or agent orchestration is needed.

### Goals: deterministic current-pace scenarios

Maintain a separate goal-allocation record. Earmarking existing money changes its intended use; it does not create an expense.

For a fixed nominal savings target:



$$\text{months remaining}
=
\left\lceil
\frac{\text{target}-\text{funded amount}}
{\text{monthly contribution}}
\right\rceil$$



Use:

- Actual net contributions to that goal.
- The user’s chosen future allocation.
- Reviewed financial history and known commitments.
- Separate handling of initial funding and one-off contributions.

Multiple goals share one contribution budget. CashNarra must not assign the same GH₵500 monthly capacity to three separate goals.

If records are insufficient, show an explicitly assumed contribution scenario. If sustainable contributions are zero/negative, or material debt commitments are unknown, withhold a useful completion date.

Debt projections require applicable interest and repayment terms. Changing targets and allocations retain their previous assumptions so date changes can be explained.

**A range calculated from GH₵300 versus GH₵400 monthly contributions is a scenario range. It is not a statistically validated forecast interval.** More recorded days do not automatically establish forecast confidence.

### Voice: short clips after text works

Choose **short recorded clips followed by transcription**, rather than live conversational audio.

A practical first implementation:

- Start with a 60–90 second recording limit.
- Cap uploaded audio at **3 MB**.
- Check recording formats using `MediaRecorder.isTypeSupported()`.
- Require HTTPS and microphone permission.
- Offer text entry or file selection when recording is unavailable.
- Let users review the transcript before financial extraction.
- Release the clip after successful processing; retain no audio archive by default.

OpenAI’s current file-transcription documentation recommends `gpt-transcribe`, accepts supported formats including MP4/M4A/WebM, and allows files up to 25 MB. CashNarra’s smaller cap accommodates Vercel’s request limit. Browser recording formats still need device testing. ([developers.openai.com](https://developers.openai.com/api/docs/guides/speech-to-text?utm_source=chatgpt.com), [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static?utm_source=chatgpt.com), [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia?utm_source=chatgpt.com))

Live audio adds session management, reconnection, interruption handling, and additional privacy/cost questions. It earns its place only if short clips demonstrably constrain the product.

Evaluate representative Ghanaian samples: accents, noisy shops, names, “MoMo,” “two-five,” “4k,” corrections, and code-switching. Measure **amount accuracy, event meaning, clarification quality, and correction effort**, not transcription accuracy alone. Do not advertise local-language support before testing it.

### Offline capture, security, and recovery

A PWA still requires explicit implementation of installation metadata, service-worker behaviour, offline storage, and synchronisation. Browser storage can be evicted and is not a backup. ([nextjs.org](https://nextjs.org/docs/app/guides/progressive-web-apps?utm_source=chatgpt.com), [developer.mozilla.org](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria?utm_source=chatgpt.com))

The first release should:

- Save text drafts locally on opted-in private devices.
- Show **“Saved on this device,” “Waiting for connection,” “Needs review,”** and **“Posted.”**
- Reuse request IDs during retries.
- Keep drafts outside financial totals.
- Synchronise/process when the app is open and connected.
- Avoid relying on background sync.

For shared devices, use a session-only mode without persistent financial caches. Logout should warn about unsynchronised drafts and clear local data. Device/browser access remains a privacy limitation; client-side encryption with a key stored beside the data does not solve it.

On the server:

- Verify authentication tokens; do not authorise from an unchecked session object.
- Scope every record by workspace and verify ownership/membership.
- Enable RLS on exposed tables.
- Use user-scoped access for ordinary requests.
- Reserve privileged secrets for narrow administrative jobs.
- Review views and privileged SQL functions separately.
- Keep secrets server-side, administrators individually authenticated with MFA, and support access recorded.

Supabase documents that privileged access can bypass RLS, and that views/functions can unintentionally bypass tenant protection. ([supabase.com](https://supabase.com/docs/guides/database/postgres/row-level-security?utm_source=chatgpt.com), [supabase.com](https://supabase.com/docs/guides/database/functions?utm_source=chatgpt.com))

**Disable shared caching for authenticated financial responses and responses setting session cookies.** Supabase warns that caching these responses can expose another user’s session. Cache public application assets only. ([supabase.com](https://supabase.com/docs/guides/auth/server-side/nextjs?utm_source=chatgpt.com))

Version migrations in the repository, apply them first to a separate development/staging database, and test restoration before onboarding real financial records.

Supabase Pro supplies seven days of daily database backups. **Those backups exclude actual Storage objects.** Before retaining receipts or other evidence, add and test a file-backup process that restores files and their database references together. ([supabase.com](https://supabase.com/docs/guides/platform/backups?utm_source=chatgpt.com))

Daily backups mean potentially losing roughly a day’s changes. Document that limitation for the pilot. Keep periodic encrypted recovery copies under company control and perform restores in isolation. Apply the deletion register before reopening restored data.

### Runtime limits and necessary jobs

Vercel Pro’s generally available maximum function duration is 800 seconds; the larger extended limit is beta. The request/response payload maximum is 4.5 MB. Set bounded application timeouts, such as 120 seconds, and keep exports paginated or generated locally. ([vercel.com](https://vercel.com/docs/functions/limitations?utm_source=chatgpt.com), [vercel.com](https://vercel.com/docs/functions/limitations?utm_source=chatgpt.com))

Use Supabase’s HTTP API/RPC for ordinary application access, avoiding a new PostgreSQL connection for each serverless request. If direct SQL access is later added, use appropriate pooling.

Scheduled maintenance needs a secret-protected endpoint, database locking, and resumable processing. Vercel cron delivery is best effort and can miss or duplicate runs; make each run safely recheck outstanding work. ([vercel.com](https://vercel.com/docs/cron-jobs/manage-cron-jobs?utm_source=chatgpt.com))

A separate worker becomes appropriate for long imports, substantial file backup, or processing that must finish reliably after the request ends.

Logs should contain IDs, timings, status codes, and error categories. Avoid raw narration, recordings, account balances, SQL parameters, and financial content in analytics.

### Audit history and deletion can coexist

| Data | Practical initial treatment |

## E. One end-to-end example

For this example, assume a non-VAT-registered business. Existing records include Sandra’s GH₵700 receivable and yesterday’s GH₵150 cash transport payment.

The user types:

> “Today sales were 3,800. Two thousand came by MoMo and Samuel still owes 450. Bought 900 stock and paid 120 transport cash. Moved 500 cash to MoMo. My brother gave the business 2,000 in the bank. Sandra paid her 700 by MoMo. Took 200 home. Put 1,000 towards the second shop. Yesterday’s 150 transport was actually 105.”

**AI identifies proposed events and material questions:**

- Is Samuel’s GH₵450 included in the GH₵3,800?
- Is the brother’s GH₵2,000 a loan or owner contribution?
- Does “put 1,000 towards the shop” mean earmarking or a payment?
- Does the correction refer to the identified earlier transport record?

After clarification, the user confirms:

- The credit sale is included; today’s remaining cash receipts were GH₵1,350.
- The GH₵2,000 is a loan; repayment terms remain unknown.
- The GH₵1,000 earmarks existing available money.
- The earlier transport record is the correct one.

The review shows:

| Confirmed record | Effect |
|---|---|
| Sales GH₵3,800 | GH₵2,000 MoMo + GH₵1,350 cash + GH₵450 receivable |
| Stock GH₵900 cash | Stock acquired; cash decreases |
| Transport GH₵120 cash | Operating expense |
| Transfer GH₵500 | Cash decreases; MoMo increases |
| Loan GH₵2,000 bank | Bank increases; liability increases |
| Sandra settlement GH₵700 | MoMo increases; old receivable closes |
| Owner withdrawal GH₵200 cash | Cash decreases; separate from operating expenses |
| Goal allocation GH₵1,000 | Goal funding changes; no spending |
| Earlier transport correction | Reverse GH₵150, replace with GH₵105 |

The user taps **Save all**.

Deterministic posting and calculations produce:

- Today’s cash change: **−GH₵370**.
- MoMo change: **+GH₵3,200**.
- Bank change: **+GH₵2,000**.
- Total cash-account change today: **+GH₵4,830**.
- New receivable: **GH₵450**.
- New loan liability: **GH₵2,000**.

The earlier correction increases the recorded cash position by GH₵45 and changes the earlier expense report. It does not create a new receipt today.

CashNarra cannot calculate profit without the necessary stock-consumption and other accounting information.

Suppose the shop goal is GH₵12,000, previously funded with GH₵2,000, with a historical/user-selected GH₵300 monthly allocation. Earmarking GH₵1,000 raises funding to GH₵3,000:



$$(12{,}000-3{,}000)/300=30\text{ months}$$



CashNarra can display:

> “At GH₵300 per month, the remaining amount takes about 30 months. Your new loan’s repayment terms are not recorded yet, so I cannot confirm whether that pace remains sustainable.”

**AI interpreted and explains. The application/database authorised, posted and calculated.**
